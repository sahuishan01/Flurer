# Workflow
- After pushing code to GitHub, monitor the CI/build status before considering the task done. Confidence: 0.65
- Do not commit/push automatically — wait for explicit user approval, then run the full commit → push → watch CI → version bump flow. Confidence: 0.60
- Release sequencing for auto-build: push the feature commit to main first (no bump), watch Build CI to green, then bump the version, commit locally, and push ONLY the annotated tag (e.g., `git tag -a v0.4.163 && git push origin v0.4.163`) to trigger Release CI; after Release CI passes, push the version-bump commit to main and verify the published release assets. Confidence: 0.75
- Write Conventional Commits (`feat(scope): …`, `chore(release): vX.Y.Z`) with a `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer; releases are annotated tags `vX.Y.Z`. Confidence: 0.70
- On task completion, send a summary notification to ntfy (https://ntfy.algosculptor.com/agent-tasks, Title "<project> (<hostname>)") with a short bullet list of what was done. Release summaries go to the dedicated agent-releases channel instead (Title "<project> vX.Y.Z Released (<hostname>)"). Confidence: 0.60
- Agent tokens/credentials (e.g., ntfy bearer token) are canonically stored in `~/.dotfiles/agent-profile/PROFILE.md`; when a token embedded in project files like AGENTS.md fails or looks stale, check there first. Confidence: 0.80
- When typecheck/build reports errors, verify they are pre-existing (e.g., git stash, re-run, stash pop) before claiming the change introduced none — report pre-existing counts separately. On Flurer the baseline is stable across runs (TS6133 unused-var warnings plus one at SettingsPanel.tsx ~line 191), so after verifying once, later runs grep it out directly (`| grep -v "TS6133\|SettingsPanel.tsx(191"`) and only inspect the remainder. Confidence: 0.70
- On the Flurer dev host, cargo check cannot run (missing GTK/glib system deps); verify Rust changes by inspection/frontend builds and defer compile validation to CI. Confidence: 0.60
- Persisted enum-like settings must degrade gracefully on unknown values: serde fallback (e.g., #[serde(other)]) in Rust plus runtime validation with a safe default in the frontend, so one corrupt value never resets all settings. Confidence: 0.55
- A debounced/scheduled settings save dies with the process: when a user action exits the app (elevated relaunch, quit), a pending debounced save never fires and the just-toggled flag is lost (user hit exactly this with `launchAsAdmin`). Fix pattern: persist synchronously in the frontend handler BEFORE invoking the exit command, and have the backend command also flush in-memory state to disk as a backstop (log flush failures, don't block the exit). Confidence: 0.6
- User-reported Flurer bugs reproduce only on the user's Windows machine; the dev host is headless Linux with no GUI, so UI bugs cannot be reproduced locally. When the root cause isn't findable by inspection, ship diagnostics instead of a speculative fix — forward webview window.onerror/unhandledrejection plus breadcrumbs into the existing file logger (e.g., a `log_frontend` Tauri command) in the next released build, then have the user re-run and paste the log. Confidence: 0.65
- The user communicates in terse one-liners (bug reports, directives) with no repro steps or context, and expects the agent to own each request end-to-end — investigate, implement, verify, release, notify — without step-by-step guidance. Confidence: 0.60
- Custom in-app window controls in Tauri require explicit capability grants (`core:window:allow-minimize`, `allow-toggle-maximize`, `allow-close`, `allow-start-dragging`) added to `capabilities/default.json` in the same change as the UI. Confidence: 0.60
- A "still broken" report immediately after a released fix ("icons are still not visible" minutes after v0.4.167 shipped) means the fix may never have reached the user's running build — before re-tuning the same values, first check which build the user is actually on (did the release install / is the updater picking it up) and whether the change is actually applied at render time (selector overridden, wrong element targeted), then only re-tune values. Confidence: 0.65
- If Release CI fails on a pushed tag, do NOT burn a new version number: diagnose with `gh run view <id> --log-failed`, fix the code on main, then delete and re-push the SAME annotated tag (`git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z && git tag -a vX.Y.Z … && git push origin vX.Y.Z`) to re-trigger Release CI, re-verify the published assets after the rerun, and mention the failed run + fix transparently in the ntfy release summary. Confidence: 0.65
- When a Windows-only compile error surfaces in CI (the Linux dev host cannot compile it), verify the external crate's API paths against the crate's real source instead of guessing: extract the .crate from `~/.cargo/registry/cache/…` (`tar xzf`) and grep its module layout. Gotcha: windows-sys 0.59 has `OpenProcessToken` under `Win32::System::Threading`, not `Win32::Security`. Confidence: 0.6
- When adding a new setting, first grep how the closest existing setting is wired (e.g., `launchAtStartup`) and mirror that full stack: Rust state field with `#[serde(default)]` + Default impl, TS settings interface + defaults, App-level update handler calling `persistSettings()`, props threading through SettingsPanel → section component, checkbox toggle plus an explanatory `settings-hint` documenting the semantics (e.g., disable takes effect next launch). Confidence: 0.6
