# Workflow
- After pushing code to GitHub, monitor the CI/build status before considering the task done. Confidence: 0.65
- Do not commit/push automatically — wait for explicit user approval, then run the full commit → push → watch CI → version bump flow. Confidence: 0.60
- Release sequencing for auto-build: push the feature commit to main first (no bump), watch Build CI to green, then bump the version, commit locally, and push ONLY the annotated tag (e.g., `git tag -a v0.4.163 && git push origin v0.4.163`) to trigger Release CI; after Release CI passes, push the version-bump commit to main and verify the published release assets. Confidence: 0.75
- Flurer releases carry TWO Windows installers (NSIS `...-setup.exe` and WiX `.msi`) because `tauri.conf.json` sets `bundle.targets: "all"`. The NSIS exe is the primary artifact: the updater's `download_and_install_update` command grabs it, and MSI cannot run the per-user hooks in `installer/watchd-service-hooks.nsh` (flurer-watchd service install/stop). To ship only one, set `targets` to `["nsis"]` (or `["msi"]`). Confidence: 0.6
- Write Conventional Commits (`feat(scope): …`, `chore(release): vX.Y.Z`) with a `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer; releases are annotated tags `vX.Y.Z`. Confidence: 0.70
- On task completion, send a summary notification to ntfy (https://ntfy.algosculptor.com/agent-tasks, Title "<project> (<hostname>)") with a short bullet list of what was done. Release summaries go to the dedicated agent-releases channel instead (Title "<project> vX.Y.Z Released (<hostname>)"). Confidence: 0.60
- Agent tokens/credentials (e.g., ntfy bearer token) are canonically stored in `~/.dotfiles/agent-profile/PROFILE.md`; when a token embedded in project files like AGENTS.md fails or looks stale, check there first, then sync the stale copy in the project file to the current token (annotating PROFILE.md as the source of truth) so later runs don't repeat the 401. Confidence: 0.80
- When typecheck/build reports errors, verify they are pre-existing (e.g., git stash, re-run, stash pop) before claiming the change introduced none — report pre-existing counts separately. On Flurer the baseline is stable across runs (TS6133 unused-var warnings plus one at SettingsPanel.tsx ~line 191), so after verifying once, later runs grep it out directly (`| grep -v "TS6133\|SettingsPanel.tsx(191"`) and only inspect the remainder. Confidence: 0.70
- On the Flurer dev host, cargo check cannot run (missing GTK/glib system deps); verify Rust changes by inspection/frontend builds and defer compile validation to CI. Confidence: 0.60
- When a fix wraps existing code in a new nesting level (e.g., `if let Some(state) = app.try_state::<AppState>() { … }`), do NOT incrementally patch the indentation with a chain of edit_file calls — on the state()-before-manage() fix this took four corrective edits (mangled line join, wrong indent level, a dropped closing brace). Read the full block and replace it in ONE edit with the final formatting, then syntax-check the file with `rustfmt --check` before committing. Confidence: 0.6
- Persisted settings must degrade gracefully on unknown/missing values, so one corrupt value never resets all settings. Enum-like values: serde fallback (e.g., #[serde(other)]) in Rust plus runtime validation with a safe default in the frontend. Persisted order arrays (sidebarSectionOrder / quickAccessOrder): drop unknown ids, dedupe, and append missing ids in their default position so an old or hand-edited settings file still renders a complete sidebar — Rust side via `#[serde(default = "…")]` with a default fn, frontend side via a normalizing memo. Confidence: 0.65
- A debounced/scheduled settings save dies with the process: when a user action exits the app (elevated relaunch, quit), a pending debounced save never fires and the just-toggled flag is lost (user hit exactly this with `launchAsAdmin`). Fix pattern: persist synchronously in the frontend handler BEFORE invoking the exit command, and have the backend command also flush in-memory state to disk as a backstop (log flush failures, don't block the exit). Confidence: 0.6
- User-reported Flurer bugs reproduce only on the user's Windows machine; the dev host is headless Linux with no GUI, so UI bugs cannot be reproduced locally. When the root cause isn't findable by inspection, ship diagnostics instead of a speculative fix — forward webview window.onerror/unhandledrejection plus breadcrumbs into the existing file logger (e.g., a `log_frontend` Tauri command) in the next released build, then have the user re-run and paste the log. For stateful UI flows where plain error breadcrumbs aren't enough (v0.4.186 rename saga), first exhaust static analysis — grep EVERY setter of the suspect state (`setRenamingPath`/`setSelected`) and read the refresh/streaming paths they sit in — then instrument the feature's FULL lifecycle through a small prefixed helper (e.g. `renameDebug` → `[rename-debug]` prefix → `log_frontend`, since the packaged webview has no console) with reason-labeled trace points: every commit/cancel labeled with its trigger (`commit("enter")` / `commit("blur")` / `cancel (Escape)`), input mount/focus/blur with `isConnected` + `document.activeElement`, and background chunk arrivals while the feature is active. Mark the instrumentation TEMPORARY with a removal note at the site, commit it as `chore(debug)`, ship it as a dedicated diagnostic release, and pair the log request with the exact log path (`%LOCALAPPDATA%\.flurer\logs`) plus one or two narrowing questions (does the simple variant work — F2 on an existing folder? is it context-dependent — multiple tabs open?). Confidence: 0.7
- The user communicates in terse one-liners (bug reports, directives) with no repro steps or context, and expects the agent to own each request end-to-end — investigate, implement, verify, release, notify — without step-by-step guidance. A directive as bare as "it's still there, fix it" is full authorization to run the entire fix → commit → push → release → notify flow autonomously. Confidence: 0.7
- Custom in-app window controls in Tauri require explicit capability grants (`core:window:allow-minimize`, `allow-toggle-maximize`, `allow-close`, `allow-start-dragging`) added to `capabilities/default.json` in the same change as the UI. Confidence: 0.60
- A "still broken" report immediately after a released fix ("icons are still not visible" minutes after v0.4.167 shipped) means the fix may never have reached the user's running build — before re-tuning the same values, first check which build the user is actually on (did the release install / is the updater picking it up) and whether the change is actually applied at render time (selector overridden, wrong element targeted), then only re-tune values. Confidence: 0.65
- Flurer's window close only minimizes to the tray, so the pre-update process keeps running even after a new version is installed — a "feature doesn't exist on the latest version" report (e.g., no grab cursor on the sidebar section labels in v0.4.175) usually means the old process is still running, not a regression. Debug order: first verify the feature is actually in the shipped bundle (build and grep `dist/assets/*` for the `draggable` attribute and its CSS selector), then have the user fully exit via tray icon → Exit, relaunch, and confirm the version in Settings → Updates & About before investigating WebView2 drag quirks. Confidence: 0.65
- If Release CI fails on a pushed tag, do NOT burn a new version number: diagnose with `gh run view <id> --log-failed`, fix the code on main, then delete and re-push the SAME annotated tag (`git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z && git tag -a vX.Y.Z … && git push origin vX.Y.Z`) to re-trigger Release CI, re-verify the published assets after the rerun, and mention the failed run + fix transparently in the ntfy release summary. Confidence: 0.65
- When a Windows-only compile error surfaces in CI (the Linux dev host cannot compile it), verify the external crate's API paths against the crate's real source instead of guessing: extract the .crate from `~/.cargo/registry/cache/…` (`tar xzf`) and grep its module layout. Gotcha: windows-sys 0.59 has `OpenProcessToken` under `Win32::System::Threading`, not `Win32::Security`. Confidence: 0.6
- When adding a new setting, first grep how the closest existing setting is wired (e.g., `launchAtStartup`) and mirror that full stack: Rust state field with `#[serde(default)]` + Default impl, TS settings interface + defaults, App-level update handler calling `persistSettings()`, props threading through SettingsPanel → section component, checkbox toggle plus an explanatory `settings-hint` documenting the semantics (e.g., disable takes effect next launch). Confidence: 0.6
- "Undo the last push and release" means a true rollback, not a forward commit: delete the GitHub release (`gh release delete vX.Y.Z --yes`), delete the remote and local tags (`git push origin :refs/tags/vX.Y.Z && git tag -d vX.Y.Z`), `git reset --hard <last-good-sha>` and `git push --force origin main`. Force-pushing main and deleting a published release are authorized by such an explicit undo request; the Build workflow re-running on the force-pushed commit is expected and harmless. Distinct from "revert it and bump" (forward revert commit + new version). Confidence: 0.6
- When a released fix for a webview-only bug fails a second time, do NOT iterate guesses on the same mechanism's quirks: the re-attempt should switch to a fundamentally more dependable primitive and carry diagnostics in the same release. Pattern from the sidebar-drag saga: instead of more DataTransfer theories, drag state moved to module-level variables AND a `dragstart` breadcrumb went through `log_frontend` to the file logger, with the escalation decision tree stated to the user up front (check `%LOCALAPPDATA%\.flurer\logs` for the breadcrumb after a drag attempt — if it's absent the events themselves aren't firing, and the next step is a pointer-event-based rewrite). Renaming-saga refinement (v0.4.182's fix shipped and still failed — "It's still not working"): before the re-attempt, source-verify the mechanism — when it can be pinned down deterministically, dig into the framework's REAL behavior rather than patching the same guess again (grep the installed package source, e.g. `grep -rn "delegateEvents" node_modules/solid-js/web/dist/web.js`, check the pinned version in package.json, and read the app entry for listener-registration order), then fix the true root cause; one verified root cause can explain several symptoms at once, and an existing guard may already cover the failure mode, so the fix is to make that guard's precondition true, not to add another guard (the global keydown handler already skipped focused inputs — the input just never got focus). Reserve the primitive-swap + diagnostics playbook for when source/logs cannot pin the mechanism down. Confidence: 0.6
- When a bug remains unresolved after multiple fix attempts, the user wants a persistent handoff artifact: write a `problem.md` at the project root stating what's wrong and what was done to try resolving it ("It still hasn't been resolved. Write a problem.md file stating what's wrong and what you did to try resolving it"). The structure that works (Flurer rename-saga problem.md): Symptom with exact repro steps → Affected code paths (file + the specific functions) → Key architectural facts that constrain the bug (e.g., how `refresh()` streaming works, Solid `<For>` reference-keying, blur-commit) → Attempted fixes, one section per shipped version (theory + what each attempt ruled out) → Remaining hypotheses (ordered, discriminable) → Next steps keyed to the evidence that would settle each (which `[rename-debug]` trace line confirms which hypothesis), plus a reminder to remove the temporary instrumentation once fixed. Commit, push, and ntfy-summary the doc so the unresolved state survives the session and can be picked up later. Confidence: 0.75
- After a tag push, choose the CI run to watch by WORKFLOW NAME **and** the tag/branch, never by recency: `gh run list --repo <org/repo> --workflow=Release --branch vX.Y.Z --limit 1 --json databaseId` then `gh run watch <id> --repo <org/repo> --exit-status`. On v0.4.183, grabbing the latest run with plain `--limit 1` followed the Build run (triggered by the accompanying main push) instead of the Release run, wasting a watch cycle; on v0.4.184, `--workflow=Release --limit 1` WITHOUT a branch filter still grabbed the PREVIOUS tag's Release run — the new run wasn't registered yet when queried, so the watch "passed" against the wrong run and the real v0.4.184 run had to be re-watched explicitly. The gh flag is `--branch`, not `--head-branch`. Robust remedy (v0.4.185): don't query-once-then-watch at all — poll until the new run registers, then watch, in one monitor command: `until rid=$(gh run list --repo <org/repo> --workflow=Release --branch vX.Y.Z --limit 1 --json databaseId --jq '.[0].databaseId // empty' 2>/dev/null) && [ -n "$rid" ]; do sleep 5; done; gh run watch "$rid" --exit-status --interval 30`. Confidence: 0.7
- Update the graphify knowledge graph as part of the pre-commit flow: run `graphify update .` at the repo root before `git add`/`git commit` (stated as "per the project workflow"). Confidence: 0.6
- A declined plan-approval prompt with no stated reason is not a rejection of the plan content — it may be an accidental/mistaken decline. When the user says "ask again for approval", re-present the SAME plan unchanged; don't interrogate with "what would you like changed?" or assume revisions are needed. Only treat it as feedback to revise when the user actually names what to adjust. Corollary from v0.4.192: when the approval prompt itself is stuck (declined repeatedly by the tooling, user reporting "I am unable to do ctrl+a in there") and the user then grants verbal autonomy ("Approve and implement it on your own"), that message IS the plan approval — proceed straight to implementation without re-presenting the plan, re-prompting, or re-asking "what would you like changed?"; all approval round-trips stop the moment the user grants verbal autonomy. Confidence: 0.65
