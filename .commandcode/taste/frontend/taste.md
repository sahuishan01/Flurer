# Frontend
- Use SolidJS for lightweight dashboard apps. Confidence: 0.70
- Prefer blended, custom window chrome over native title bars: undecorate the windows (`decorations: false`) and carry the OS drag region plus min/max/close controls inside the app's own top bar, styled platform-fluent (flat buttons, red close hover), so no unstyleable native chrome shows above the app shell. Confidence: 0.70
- Prefer compact UI chrome with maximum glyph visibility; oversized or dimmed chrome gets rejected round after round: full-height 46px Win11 window-control blocks were "too large" (accepted: ~30×26 rounded pills), the follow-up titlebar styling that left the top bar taller than before (0.75em padding) with faint `--text-secondary` glyphs was rejected outright ("too much height, icons not visible"), and icon visibility was STILL reported broken ("icons are still not visible") even after the full-contrast/1.4px stroke fix — thin stroked SVGs are just not reliably visible at ~11px on some DPIs. Accepted solution (user-directed: "you can use colors rather than icons for easier visibility"): draw window-control glyphs as solid filled CSS shapes instead of stroked SVGs — filled 10×2px bar (minimize), 9×9px box with 2px border (maximize), close X built from two 2px-thick rotated bars — all in full-contrast currentColor / `--text-primary`. General rule for small chrome glyphs: solid filled shapes / color blocks beat thin line icons; when a glyph must stay visible at small sizes, don't reach for stroked SVGs at all. Top bar stays at its pre-titlebar compact height (~0.35em vertical padding). When restyling chrome, err smaller and higher-contrast than the platform default. Confidence: 0.85
- Custom top-bar chrome must remain fully functional through any restyle: the window must stay draggable by the top bar (preserve `data-tauri-drag-region` on the bar and its non-interactive children across markup restructures — a restyle silently dropped it and the user immediately reported "unable to drag") alongside the min/max/close buttons. Confidence: 0.7
- Theme switching must visibly restyle the whole UI surface, not just the accent — the user reported it as a bug when changing theme left borders, text, file-manager lines, and buttons unchanged, and again when sidebar selection text and recents stayed yellow. Coverage must be exhaustive: component-scoped hardcoded accent overrides count as bugs even when they are leftovers from an earlier experimental "design pilot" (a warm-amber accent scoped to `.sidebar`/`.command-bar`); the user expects them deleted so every region inherits the theme's accent tokens. Implement by giving each named theme (Midnight/Ocean/Nord/Paper) its own overrides of the semantic surface tokens (`--border-color`, `--border-strong`, `--hover-bg`, `--active-bg`, `--scrollbar-thumb*`) in `html[data-theme="…"]` blocks declared after `:root` so they win the cascade over the light/dark mode tokens, plus per-theme text colors (e.g., Paper's warm ink `#3b2f22`) which must carry `!important` to beat the `data-bg-lightness` text overrides in theme.css. When a region "doesn't follow the theme", first grep the CSS for hardcoded hex accent values / scoped `--accent` overrides before touching the theme system. Confidence: 0.8
- Flurer theming architecture (established by the multi-theme request): theme identity lives on `data-theme`, material lightness on `data-mode` — the shared dark base styles sit on `[data-mode="dark"]` (theme.css + App.css) so every dark-based theme (dark/midnight/ocean/nord) inherits them, and each theme contributes only its accent/tint block in theme.css. Adding a theme = extend the `THEMES` list (value/label/dark) + `isDarkTheme()` in settings.ts, extend the Rust `Theme` enum, set both dataset attributes (with a light-mode fallback for unknown persisted values) in App.tsx's createEffect, and render the picker from `THEMES` — never hardcode per-theme buttons or branch on theme names. Confidence: 0.6
- Use React / Next.js for standard web frontends. Confidence: 0.70
- Windows Explorer is the behavioral reference for Flurer's file-manager semantics — when listing behavior is ambiguous, mirror Explorer rather than inventing an interaction model. Concretely: with Group by = None the list must interleave folders and files purely by the chosen sort key (the folders-first partition only applies while a grouping is actually active); the user reported the old always-folders-first behavior as a bug ("everything is grouped using type" when sorted by modified). Confidence: 0.6
- Do NOT use HTML5 drag-and-drop for internal interactions (e.g., sidebar drag-to-reorder) in Tauri's WebView2 webview — it is rejected outright (prohibited cursor, drops never accepted) no matter how the DataTransfer is populated. Proven incrementally: the full MIME-based approach shipped (dedicated `application/x-flurer-sidebar-section` set on `dragstart`, `types.includes` gate on `dragover`, `getData` on drop) and still showed the prohibited cursor; the v0.4.178 rework tracking the drag source in module-level variables with only a plain-text DataTransfer payload ALSO failed ("still the same") — the drag events themselves are effectively dead in WebView2. Accepted solution (v0.4.179) removes HTML5 drag entirely: pointer-event-based reordering — `onPointerDown` (guard `e.button === 0`) registers `pointermove`/`pointerup` handlers on **`window`** for the whole press → window `pointermove` hit-testing with `document.elementFromPoint(clientX, clientY)?.closest("[data-section-id]")` driving live reorder as the pointer moves → cleanup on window `pointerup`. Do NOT use element `setPointerCapture` here (v0.4.180 fix): the first live reorder re-parents the dragged DOM node, which silently releases element capture and capped drags at one slot per press ("I am able to drag it only one space at a time"). Whenever the pressed element may be re-parented or mutated mid-drag, track the pointer at window level instead of relying on element capture. Preserve click semantics with a movement threshold (~6px): suppress the next click (`suppressNextQuickClick` flag) only when a drag actually happened, so non-drag clicks still navigate. Attach handlers on the grab-handle element. Hit-target granularity is user-directed and precise: as of v0.4.181 `data-section-id` lives on the header label span itself (NOT the whole section block) — block-level hit-testing was explicitly rejected ("it starts swapping as soon as I enter the whole group, but it should swap when I drag and reach just above the title of a group"). General rule for drag-reorder drop targets: the swap must fire only when the pointer reaches the target's header/title element, never when merely entering the target's container body; the drag-over highlight can stay on the container. Native file drags (tauri-plugin-drag) never fire pointerdown on these elements, so they can't collide. Pair with persisted order state plus a visual drag-over accent indicator. Confidence: 0.85
- JSX boolean attributes must be written explicitly, never bare: `<span draggable>` renders as `draggable=""`, which the HTML spec treats as an invalid value defaulting to **false** — this shipped as a real Flurer bug where sidebar drag handles were never draggable and the grab cursor never appeared, while the bundle grep for `draggable` looked fine. Always write `draggable={true}` (with a code comment at the site explaining why), and never key CSS off attribute-value selectors like `[draggable="true"]` for such attributes — use a dedicated class (e.g., `.is-grab`) instead, since the attribute selector can't distinguish the broken empty-value case. Confidence: 0.7
- Inline rename/edit inputs must be fully operational the instant they open — the user reported both failure modes as bugs: "it doesn't automatically selects the text inside the input field and the focus is somewhere else… I need to manually click once to bring the cursor" and "when I press enter it opens the folder instead of just renaming". `autofocus` only applies on initial page load, NOT for dynamically inserted elements: focus explicitly via a ref, and preselect the base name Explorer-style (`setSelectionRange(0, isFile && lastDot > 0 ? lastDot : value.length)`) so typing replaces the name while the file extension stays untouched (folders have none). Enter must commit the edit ONLY — it must never also fire the row's activation (opening the folder); Escape cancels. Hard-won Solid gotcha (v0.4.182's ref-based focus fix shipped and STILL failed — "It's still not working"): Solid invokes a ref on a conditionally-rendered element (dynamic ternary branch) at element CREATION, before the node is inserted into the DOM, and `focus()` on a disconnected element is a silent no-op — the input never got focus, so Enter kept falling through to the global row handler (which already skips focused inputs; both symptoms shared this single root cause). Correct pattern (v0.4.183): inside the ref, defer the focus + `setSelectionRange` one `queueMicrotask` so the element is attached by then. Confidence: 0.8
- When an inline editor must swallow keys that also have global handlers (e.g., rename input vs. document-level keydown): in Solid, delegated event handlers and component-registered `document.addEventListener("keydown", …)` listeners share the SAME node (`document`), and `e.stopPropagation()` does not stop *other listeners on that same node* — Enter/Escape leaked from the input's `onKeyDown` to the file-open handler even with `stopPropagation()` present. Use `e.stopImmediatePropagation()` in the editor's keydown handler. Confidence: 0.7
- Keep Solid `<For>` row identity stable across background/silent refreshes: `<For>` keys rows by reference, so a silent relist that rebuilds every object (the directory watcher's `directory-changed` relist constructing fresh `DirEntry`s per event) tears down and remounts every row — which unmounts an open inline editor mid-edit, and its blur-commit handler then closes the editor ("when I create a new folder, it shows the editing field and then automatically closes"). Fix pattern (v0.4.184): during silent relists, reuse the previous objects when their content is unchanged (compare the primitive fields — name/isDir/size/modified) so unchanged rows (and the focused input) stay mounted; verify the entry type's fields are all primitives before reusing objects. That alone was NOT enough (v0.4.185, user retest: "it's still closing as soon as I create a new folder") — the freshly created folder's row is legitimately a new object, and Chromium fires blur when a focused element is removed from the DOM, so ANY relist rebuilding the editing row unmounted the input and its blur-commit handler closed the editor. Durable guard (v0.4.185): a blur from unmount is not the user clicking away — only commit while the element is still connected: `onBlur={(e) => { if (e.currentTarget.isConnected) commitRename(); }}` (comment the site: removal-blur is spurious, not user dismissal). The guard alone still did NOT resolve the report (v0.4.185 retest: "The problem still persists… opens the input box, then instantly closes it and deselects the folder" — selection loss is an additional symptom beyond the editor closing), and even after statically tracing every `setRenamingPath`/`setSelected`-clearing path no cause was findable, so v0.4.186 shipped as a dedicated diagnostic build with `[rename-debug]` full-lifecycle tracing via `log_frontend`; root cause is pending the user's log — treat this saga as unresolved until the trace lands. Confidence: 0.75
- Settings that gate live/incremental updates must never let app-initiated actions leave stale derived state. When the user reported that deleting a subfolder didn't update the parent's cached size, the semantics were spelled out precisely: in-app deletes must update parent sizes "irrespective of the fact if the settings on or not… this is only for files/folders deleted from the app. For the rest it should be dependent upon the settings." Implement as a split: mutations issued from the UI (delete_items / delete_items_forever) always refresh affected derived state immediately (sizecache::refresh_after_app_delete recomputes every cached ancestor, bypassing the live_folder_size_updates setting), while the setting continues to gate only externally-triggered (watcher) changes. Default to this split for any setting that gates background recomputation. Confidence: 0.75
- Adding a new in-app keyboard shortcut in Flurer: extend the `InAppShortcutAction` union in `src/lib/shortcuts.ts` AND all three companion tables (human-readable label, default keybinding, `actions:` array entry) — stored shortcut settings merge with defaults, so a missing actions-array entry leaves the shortcut unusable. Handle it in the keydown flow via `bound("action")`, ordering more-specific combos before bare keys (deletePermanently before delete), and when one modal serves action variants, carry the variant flag inside the shared state signal (`deleteTargets: { paths, permanent }`) instead of adding parallel signals. Confidence: 0.6
- User-facing features must ship customizable, not hardcoded: the top-bar system-metrics request explicitly demanded "customizable option to add or remove these as per user interest" for every hardware category (with the note that users can have MULTIPLE of each device — model one-configurable-entry-per-device, not per-category), plus an on-hover detailed view for each widget. General pattern the user expects: settings-driven features (master toggle + per-device selection persisted in settings) rendered as compact always-visible indicators with detail-on-demand via hover popup — never a fixed widget set or an always-expanded panel. Confidence: 0.6
