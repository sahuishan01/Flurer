# Architecture
- For plugin installation: support direct GitHub URL entry or ZIP file upload instead of a remote marketplace registry. Confidence: 0.70
- Release and version plugins independently from the main app, not as release assets in main app builds. Confidence: 0.75
- Place all plugins under a `plugins/` directory within the main app repo, each with its own build config and package.json. Confidence: 0.75
- When bumping app version, update ALL version fields consistently (Cargo.toml, package.json, tauri.conf.json) and stage Cargo.lock alongside them. Locate each occurrence by grepping the current version string instead of trusting fixed line numbers, and verify Cargo.lock's own `flurer` entry afterwards — the lock can be silently stale (found at 0.4.162 while the other three files were at 0.4.181), so patch its `name = "flurer"` version block explicitly. Confidence: 0.75
- Tauri: lifecycle/run-event handlers that can execute before `app.manage()` must use `app.try_state::<T>()` instead of `app.state::<T>()` (which panics with "state() called before manage()"). Reachable in Flurer via the "Always run as admin" path: accepting the UAC prompt makes the unelevated instance call `app.handle().exit(0)` inside `.setup()` BEFORE reaching `manage(AppState)`, and that exit fires `RunEvent::Exit`, whose window-settings save handler used `app.state::<AppState>()` and crashed (v0.4.187). A "state() called before manage()" crash on one machine but not another points at a settings-dependent setup early-exit path, not platform flakiness — trace the setup exit paths against the manage() call-site order. v0.4.188 proved the guard must be a SWEEP, not a point patch: guarding only the settings-save site still crashed on the user's machine because the same Exit handler also calls `sizecache::flush(app)`, which had its own unconditional `app.state()` — and the guarded settings block itself was skipped on that path (no main window yet) while `flush` ran unconditionally. Before releasing such a fix, grep for EVERY call site of the panicking pattern (`.state::<`) and audit all callbacks reachable in the pre-manage window (single-instance handler, global-shortcut handler, spawn_new_window), guarding each with `try_state` + early return and a site comment stating the rationale. Confidence: 0.65
- When offered a simpler-but-partial vs. lower-level-but-complete implementation option (GPU metrics tradeoff question: "Recommended" NVIDIA-only NVML wrapper vs. all-vendor D3DKMT), the user chose the ALL-vendor D3DKMT route — prefers complete device coverage over implementation simplicity, accepting fragile low-level Windows API code, especially when it fits existing Windows-only patterns already in the codebase (WMI disk topology). Frame tradeoff questions with a recommended option, but expect the user to pick coverage when the alternative excludes hardware. Confidence: 0.55
